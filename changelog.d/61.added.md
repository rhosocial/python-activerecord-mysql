Add `MySQLColumnTypeMixin` (`mixins/column_type.py`), the column half of the rebuilt column-type protocol, composed into `MySQLDialect` alone -- core's `ColumnTypeMixin` has no inherited table for it to override, so its `MYSQL_COLUMN_TYPES` class attribute is the whole version-independent answer: every entry of the framework's common Python types is answered, the deviations from the portable baseline being `float` / `Decimal` both answering `NumericColumn` (core now models both width families with one column class, while MySQL's `DOUBLE` and `DECIMAL(p,s)` -- distinct types with distinct rounding -- remain two classes on the DDL side, which is where that measurement lives), `list` / `tuple` / `set` / `frozenset` answered with `JSONColumn` rather than core's `ArrayColumn` (MySQL has no array type on any version, so a column cannot be declared `INT[]`, while the JSON path family is measured working from 5.7), and `timedelta` answering `NumericColumn` because MySQL's `INTERVAL` is an expression keyword and never a column type. The one version-dependent cell is `dict`, which is answered `None` below 5.7 -- measured on 5.6.51, which has neither the `JSON` column type nor any JSON function (`1064` for the DDL, `1305 FUNCTION ... does not exist` for the operations), so a default there would render SQL the server refuses with the error pointing at the column rather than at the annotation; the refusal fails at model definition time naming `UseColumnType` instead, and the gate reads `MySQLJSONFunctionMixin.supports_json_path` (5.7.0, where `JSON_EXTRACT` appeared) rather than repeating the number, so the column-level answer and the expression-level one cannot drift -- while the containers keep their `JSONColumn` answer below the gate, because a sequence is not obliged to use the function family the measurement refuses. The former `supports_column_operation()` narrowing is gone with the core mechanism that carried it (`ilike` spelling, `jsonb` quantifiers and the `JSON_TABLE` gates are no longer declared anywhere; the two silent behaviours that are rendering obligations rather than missing capability -- a directly bound `=` returning zero rows without error, and 5.7's whole-column text comparison missing rows because the JSON column normalises whitespace and key order -- are recorded in the mixin's docstring for the rendering phase to inherit). Two of MySQL's best-known divergences from a textbook server are absent from the table on purpose and stated in the docstring instead: `UUID` is native on MariaDB from 10.7 and on no MySQL version, and MySQL's `JSON` *is* native from 5.7.8 where MariaDB's is a `LONGTEXT` alias -- both are storage facts belonging to `suggested_data_types()`, and gating a column class on one would be the confusion the two-layer split exists to prevent.
