Add `MySQLColumnSuggestionMixin` (`mixins/column_suggestion.py`), the column half of the suggestion protocol, composed into `MySQLDialect` ahead of core's generic mixin so its eighteen-entry `COLUMN_TYPE_SUGGESTIONS` table and its `supports_column_operation` narrowing are the ones a model layer reaches: every entry of `COLUMN_TYPE_ENTRIES` is answered, the deviations from core's neutral baseline being `float` / `Decimal` told apart (`FloatColumn` / `DecimalColumn`, where MySQL's `DOUBLE` and `DECIMAL(p,s)` are distinct types with distinct rounding) and `list` / `tuple` / `set` / `frozenset` answered with `JSONColumn` rather than core's `ArrayColumn` (MySQL has no array type on any version, so a column cannot be declared `INT[]`, while the JSON path family is measured working from 5.7); `timedelta` answers `NumericColumn` because MySQL's `INTERVAL` is an expression keyword and never a column type. The one version-dependent cell is `dict`, which is `UNSUPPORTED` below 5.7 -- measured on 5.6.51, which has neither the `JSON` column type nor any JSON function (`1064` for the DDL, `1305 FUNCTION ... does not exist` for the operations), so a default there would render SQL the server refuses with the error pointing at the column rather than at the annotation; the gate reads `MySQLJSONFunctionMixin.supports_json_path` rather than repeating the number, so the table and the expression layer cannot drift. The narrowing declares `("StringColumn", "ilike")` unavailable on every version (measured `1064` on 5.6 / 5.7 / 8.0; `like` stays available, since the default `utf8mb4_*_ci` collation already makes it case-insensitive), refuses the PostgreSQL `jsonb` quantifiers `@>` / `@?` on `JSONColumn` (MySQL's `JSON` has neither as syntax), and gates the JSON function operations on 5.7 and `JSON_TABLE`-backed `unnest` / `json_table` on 8.0.4; `json_equal` is deliberately *not* narrowed and the two silent behaviours that follow from it -- a directly bound `=` returning zero rows without error, and 5.7's whole-column text comparison missing rows because the JSON column normalises whitespace and key order -- are recorded as Phase 2b rendering obligations rather than as a missing capability. Two of MySQL's best-known divergences from a textbook server are absent from the table on purpose and stated in the docstring instead: `UUID` is native on MariaDB from 10.7 and on no MySQL version, and MySQL's `JSON` *is* native from 5.7.8 where MariaDB's is a `LONGTEXT` alias -- both are storage facts belonging to `suggested_data_types()`, and gating a column class on one would be the confusion the two-layer split exists to prevent.
